## 1. 🔴 公開前に必ず直す

### 1-1. ✅ 済（10/11）生年月日を「文字」で渡すと、別人の運勢になる
- 生年月日を数字ではなく文字（例：`"1960"`）で計算に渡すと、生まれた日の干支が別のものになる（1960年1月1日：正しくは戊子 → 戊申になる）。メールもカレンダーも全部ずれる。
- 登録データ（Google フォームの「1990-5-3」を分けたもの）は文字になりやすく、本番で起きやすい。
- 直したこと：計算の入口（engine.js の jdn・bazi.js・daily-engine.js、1.66 の index.html）で必ず数字に直すようにした。文字で渡しても数字と同じ結果になることを 1,044通りで確認。数字での結果は1つも変わっていない（開運予報 120人×3年分・1.66 の 3600組で確認）。実在しない日付（2月31日など）はエラーで止め、別人の運勢を送らないようにした。仕様書 §3-1 に「必ず数値で渡す・エラーの人は送らずに記録」を追記。

### 1-2. 本番のサーバーにつながっていない（エンジニア）
- ログイン・登録・マイページ・配信停止の4ページが「開発モード」のまま。今のままだと、ログイン用の確認コードが画面にそのまま出てしまい、**誰でも他人のメールアドレスでログインできる**。
- 登録の送り先（Google フォーム）の番号が「FORM_ID」のままで、登録内容がどこにも届かない。
- 直し方：本番の接続先を設定し、開発用の「コードを画面に出す」処理を本番では消す。

### 1-3. 登録のしくみが 100万人に耐えない（エンジニア）
- 確認コードを入れる前に保存している／保存に失敗しても気づかない作り。
- ロボット対策・回数制限がない（他人のアドレスに確認コードを大量に送られると、送信元の評判が落ちて毎朝のメールが迷惑メールに入る）。
- Google スプレッドシートは約70万人で上限に達する。
- 直し方：サーバーに登録の受け口を作る／ロボット対策（Cloudflare Turnstile）／回数制限／「仮登録 → 確認コードが通ったら本登録」にし、本登録の人にだけ毎朝送る。

### 1-4. マイページの生年月日が、その端末の中にしかない（エンジニア）
- 新しいスマホでログインすると、仮の生年月日（1995/6/15）のカレンダーが出て、メールと合わなくなる。
- 体験ページで別の生年月日を入れると、ログイン中の人のマイページのカレンダーも変わってしまう。
- 「関心はあとからマイページで変えられます」とあるが、変える画面がない。
- 直し方：ログイン中は、サーバーの会員データ（生年月日など）を使う。会員データを取る・関心を変える・メールを変える、の受け口を仕様書に追加。

### 1-5. メールに「送信者の住所」へのたどり着き方がない（オーナー判断＋エンジニア）
- 毎朝のメールには自社の案内（Special Reading・公式LINE）が入るため、法律（特定電子メール法）上「広告宣伝メール」にあたり、**送信者の名称・住所・連絡先・停止方法**の表示が必要（住所はリンク先のページでよい）。
- 今のリンク先（運営者情報）には住所がない（無料サイトには住所を出さない方針のため）。
- 直し方の案：メールからだけ開ける「送信者情報」ページ（検索に出ない設定）を作り、そこに住所（バーチャルオフィス可）を書く。→ **オーナーの判断が必要**。

### 1-6. 1.66 で 5回目から「登録の壁」が出て、登録した人も通れない（私）
- 1.66 は4回まで診断でき、5回目から「ご登録で回数制限なし」という画面が出る。
- 登録は unkiyoho.jp で行うので、1.66 側では登録済みかどうかがわからず、**登録した人にも毎回この壁が出る**。
- 「回数制限なし」という書き方は「登録すると機能が増える」ように読め、広告の「登録なしでOK」とも合わない。
- 直し方の案：回数制限をなくし、「毎朝の予報もいかがですか？（料金はかかりません）」のおすすめだけにする。→ **オーナーの判断が必要**。

### 1-7. 1.66 の小窓（体験ページ）から登録へ進むと、小窓の中で開いてしまう（私）
- 1.66 の中で開いた「今日の運勢（体験）」から「登録」「マイページ」に進むと、小窓の中で開く。小窓の中ではログインがうまく動かない（ブラウザの決まりで、別サイトの中ではログインの情報が使えない）。
- 直し方：小窓の中で開いたときは、リンクを画面全体で開くようにする。

### 1-8. アクセス解析が1つも入っていない（オーナー＋エンジニア）
- 何人来て、何人が診断し、何人がシェアし、何人が登録したかが、まったく測れない。紹介コード（?ref=）も端末に残るだけで、どこにも送られていない。
- 直し方：Google アナリティクス（GA4）を両サイトに入れ、2つのサイトをまたいで追えるようにする。測る動き：診断・シェア（X・LINE・画像・コピー）・登録・確認完了・体験。1.66 から登録へのリンクに `?ref=166`、メールのリンクにも目印を付ける。
- 解析を入れたら、プライバシーポリシーにも書く。

### 1-9. プライバシーポリシーの「外部への送信」の書き方（私）
- 今は「詳しくはご請求に応じて開示」となっているが、法律（電気通信事業法の外部送信の決まり）では、**いつでも見られる場所に書いておく必要がある**。
- 実際に送っている先：Google Fonts（文字の形の読み込み）、Google フォーム（登録内容）、メール配信会社。これらが書かれていない。
- 直し方：送信先・送る情報・目的を表にしてポリシーに載せる（文字の形を自分のサーバーから配れば、Google Fonts への送信自体をなくせる）。

### 1-10. ワンクリック配信停止の受け口が決まっていない（エンジニア）
- Gmail・Yahoo は、大量送信者に「メールの一覧からワンクリックで停止」を義務づけている。今の配信停止ページはその形式の受け取りができない。
- 直し方：停止用の受け口を作り、仕様書に詳しく書く（停止トークンの作り方、mailto で来た停止の扱いも）。

## 4. エンジニアに頼むこと（仕様書に追記する）
