## 2-9. 第9版：毎朝30万通を届けるための「送信の立ち上げと監視」

毎日メールは、**迷惑メールに入らずに届き続けること**がすべての前提です。Gmail・Yahoo は 2024年から、1日5,000通以上送る送信者に次を**必須**にしています。1万人を超えた時点で対象になります。

### A. 送る前にそろえるもの（必須）
- 送信元ドメイン（例：`mail.unkiyoho.jp`）の **SPF・DKIM・DMARC**（DMARC は `p=none` から始めて、レポートを見て `quarantine` へ）。From のドメインと DKIM のドメインをそろえる。
- **ワンクリック配信停止**：`List-Unsubscribe: <https://unkiyoho.jp/unsubscribe?token=…>, <mailto:…>` と `List-Unsubscribe-Post: List-Unsubscribe=One-Click`。**停止は2日以内に反映**（本サービスは即時）。
- **迷惑メール報告率 0.1％未満を目標、0.3％を絶対に超えない**（超えると Gmail で受信拒否・迷惑メール行きになる）。
- 送信元IPの逆引き（PTR）。送信サービス（Amazon SES／SendGrid 等）を使えば通常は設定済み。

### B. 立ち上げ（ウォームアップ）
- 新しいドメイン・IPから、いきなり数万通を送らない。**最初の2〜4週間は、1日の送信数を少しずつ増やす**（目安：前日の1.5〜2倍まで）。
- 会員が少しずつ増える間は自然にウォームアップになる。**キャンペーン・SNSで一気に登録が増えた日**は、新しい会員への送信を数日に分けるなど、急増させない。
- 専用IPを使う場合は、送信サービスの自動ウォームアップ機能を使う。1日数万通までは共有IPでもよい。

### C. 毎日見る数字（監視）
| 数字 | 見る場所 | 目安・対応 |
|---|---|---|
| 迷惑メール報告率 | **Google Postmaster Tools**（ドメインを登録）／送信サービスの苦情通知（Yahoo・Outlook の FBL） | 0.1％を超えたら原因を調べる。0.3％に近づいたら送信を減らす |
| ドメイン・IPの評判 | Google Postmaster Tools | 「低い」「悪い」になったら送信数を減らして原因を調べる |
| 不達（バウンス）率 | 送信サービス | **ハードバウンス（存在しないアドレス等）は即、配信停止リストへ**。ソフトバウンス（受信箱がいっぱい等）は3回続いたら停止。不達率2％超えは要注意 |
| 苦情（迷惑メール報告）した人 | 送信サービスの通知 | **即、配信停止**にする（二度と送らない） |
| 開封・クリック | 送信サービス | iPhoneは開封が多めに出るので、クリックもあわせて見る |

- **長く読まれていない会員**（例：90日クリックなし）には、「このまま受け取りますか？」の確認メールを1回送り、反応がなければ配信を止める。届く率が上がり、送信費用も下がる。
- 携帯キャリアのメール（docomo・au・SoftBank）は受信設定が厳しいので、登録完了画面に「`@unkiyoho.jp` からのメールを受け取れるように設定してください」の案内を出すとよい。

### D. 30万通を毎朝6時までに届ける
- 文面づくり（`generateDaily()`＋`renderDailyMail()`）は1通あたり約4ミリ秒（実測）。30万通でも1台で約22分（並列にすればさらに短い）なので、**3時ごろから作っておき**、送信だけを後にする。
- 送信は **4時30分ごろに開始**し、6時までの90分で送り切る＝**毎秒約60通**。送信サービスの**送信上限（1日の通数・1秒あたりの通数）を事前に引き上げておく**（Amazon SES なら本番利用の申請と上限引き上げの申請）。
- 途中で失敗しても、同じ会員に2通届かないように「送信済み」を記録してから次へ進む（再実行しても二重送信しない）。
- 画像（`mail-bg/`）は CDN 経由・長めのキャッシュ（§5）。30万人・開封率50％でも、1通約30〜70KBなら**毎月約0.1〜0.3TB**（写真のころの約1TB以上から大きく減る）。

## 3. なぜこうなったか（原因）

**原因はすべて、こちらからお渡しした資料の側にあります。** 実装が資料に従わなかったのではなく、資料の中に「正しいもの」が複数あって、互いに食い違っていました。

### 原因1：「本文の正」と「見た目の正」が別のファイルで、中身が食い違っていた
- 仕様書 §10.2 には、2つのことが書かれていました。
  - 「本文は **`my-tenki-demo.html` の `run()`** が組み立てる本文と**完全に同一**」
  - 「見た目の目標は **`mail-sample.html`**」
- この2ファイルは、**並んでいる項目も見出しも違います。** `my-tenki-demo.html` はアプリ画面のデモで、今日の月・七十二候、鑑定、学び、ジャンル見出しなどがありません。
- エンジニアさんは「完全に同一」と強く書かれた前者に従ったため、**項目が足りず、並びもデモ画面と同じ**になりました。ヘッダーの紺色の帯「MY DAILY FORECAST」も、`my-tenki-demo.html` のデザインです。

### 原因2：メールでそのまま使えるひな形を渡していなかった
- `mail-sample.html` は**Webページ**です。JavaScriptで月の便箋を切り替え、グラデーション・影・グリッドで見た目を作っています。メールではJavaScriptが動かず、GmailはCSSの多くを削ります。
- 資料には「テーブルレイアウト＋インラインCSSへ移植」「Web用CSSなので**構造の参考に**」としか書いておらず、**移植済みのひな形はありませんでした。**
- そのため、エンジニアさんが見た目をゼロから組むことになり、見本と違うデザインになりました。

### 原因3：件名の書き方が2通りあった
- 仕様書 §10.2 の件名例：`【7/9(木)】あかりさんの今日の運勢🌤`
- バックエンド仕様書 §4-4：件名＝`generateDaily().subject`
- 実装は前者を使っていました。**オーナー決定で「両方を組み合わせる」形に確定しました**（§1）。

### 原因4：季節の背景の設定が、見本ファイルごとにバラバラだった
- `mail-sample.html`：写真は **1・2・3・8月の4か月だけ**。ほかの月は色と絵文字だけ。
- `mail-sample-free.html` と `my-tenki-demo.html`：**12か月すべて写真**（オーナーが用意した `bg-*.jpg`）。
- 同じ「見本」なのに設定が違っていました。当時は「12か月すべて写真」に統一しました。**第9版で、写真はやめて「動く季節バナー＋月ごとの色」に変わりました**（§1・§2-8）。

### 原因5：「無料版」という名前の古い見本が混ざっていた
- `mail-sample-free.html` は「無料版」という名前ですが、**このサービスは全員無料で、有料版・無料版の区別はありません。**
- また、このファイルは**エンジンとつながっていない固定の見本文**です（9月でも7月の「大暑」が出る）。
- 名前が誤解を招くので、メールの参考にはしないでください。

### 原因6：フッターの記載が、オーナーの決定と違っていた
- 引き継ぎ資料には「法定フッター：事業者名・**住所**」と書かれていました。
- オーナー決定は「**住所は載せない。会社名とメールアドレスはリンク先のページ（`tokushoho.html`）に載せる**」です。メール本文には「運営：72k株式会社｜運営者情報」だけを小さく入れます。

## 6. 間違えやすい点（必ず確認）

- **性別は `'f'`／`'m'` に変換して渡す**（登録の値は「女性」「男性」）。間違えると男性に女性向けの服・恋愛運が届き、縁の計算も変わる（§2-4）。
- **`interests`（関心）は、登録フォームの日本語の値をそのまま渡す。** 例：`['恋愛', '仕事・キャリア']`
  - 使える値：恋愛／結婚／友達づくり／仕事・キャリア／習い事・勉強／投資／お金・家計／健康・ウェルネス／ヨガ・ピラティス
  - 英語（`love` など）に変換して渡すと、エンジンが読み取れず「🎯今日の注目テーマ」が出ません。こちらの見本作成でも、一度この間違いをしました。
- **`personBazi: PersonBazi` を必ず渡す。** 渡さないと運勢のランクが運命カレンダーとずれます。
- **日付はJSTで渡す。** UTCだと干支が1日ずれます。
- **テンプレートの見た目を変えるときは、グラデーション（background-image）を文字の下に使わない。** ダークモードで「明るい背景に明るい文字」になり、読めなくなります。背景は単色で指定してください。
- **`my-tenki-demo.html` はアプリ画面のデモです。メールの見た目・並びの参考にしないでください。**
- **カレンダーの核となる記号・絵文字は、絶対に変えない・消さない（オーナー決定）。** ランクの 💮◎〇△ と、分野のマーク（🌈 運命の人の日／🌷 出会い・モテ運の日／🌸 恋が動く日／🩷 魅力が輝く／💰 金運／💼 勝負運／🌐 対人運／📚 学び など）は、運命カレンダー・毎朝のメール・**ほかの商品とも連動**しています。古い端末で表示できない絵文字があっても、置き換えずにオーナーに相談すること。
- **`refCode`（会員の紹介コード）を渡す。** 渡さないとシェアのリンクが `?ref=mail` になり、だれの紹介か分からなくなる（第9版）。
- **写真の背景をメールに戻さない。** 1通が約500KBになり、30万人では毎月1TB以上の転送になる（第9版。写真 `bg-*.jpg` は廃止・削除済み）。
- エンジンの文章を書き換えたり、項目を足し引きしたりしない。変更が必要なときはオーナーに確認する。

## 9. 資料の運用ルール（同じ間違いを繰り返さないために）

今回の原因は「正しいとされる資料が複数あり、互いに食い違っていたこと」でした。今後は次のルールを守ります。

1. **毎朝メールの正は、この資料と `mail-template/` だけ。** 仕様書・引き継ぎ資料・見本HTMLにメールの記述があっても、この資料と違えばこの資料が正しい。
2. **変更は「この資料」と「`mail-template/`」を同時に直す。** 片方だけ直すと、また食い違いが生まれる。見本（`samples/`）も必ず作り直す。
3. **見本は必ずロジック（`generateDaily()`）で生成する。** 手で書いた固定の見本文は作らない（`mail-sample-free.html` の失敗の再発防止）。
4. **「完全に同一」「必ず」と書くときは、何と同一なのかを1つだけ書く。** 2つの資料を別々に「正」と呼ばない。
5. **本番に出す前に、§8 のチェックリストを全部確認する。** 特に `sample-0924-test-married` との完全一致。
6. **資料に書いていないことを判断するときは、自己判断で決めずオーナーに確認する。**
7. **カレンダーの記号・絵文字（💮◎〇△・分野マーク）は変えない・消さない。** ほかの商品と連動しているため（オーナー決定）。
8. **ロジックの文言（料理・場所・アイテム・行動など）を足したり変えたりしたら、必ず `check-quality.js` を実行して PASS を確認する。** FAIL のまま配信しない。
