# 認証（ログイン）機能 実装引き継ぎ書

- 対象：「私だけの運気予報」（unkiyoho.jp）
- 目的：エンジニアから指摘のあった **「ログイン画面がない／登録メール間違いの復旧がない／マイページに認証がない」** の3点を実装するための、フロント実装内容とサーバーAPIの仕様。
- 方式：**パスワードレス（メール確認コード / OTP）**。仕様書 `仕様書_エンジニア向け_相性診断と運気予報.md` §10・§12、`公開前TODO-エンジニア.md` ⑥ の「パスワードレス（マジックリンク／OTP）推奨」に準拠。
- 状態：**フロントは実装済み**。空の `UNKIYOHO_AUTH_API_BASE` により、いまは**開発モード**（ブラウザ内だけで動作／メール送信なし）で動きます。**サーバーAPIを実装し、URLを設定するだけ**で本番動作に切り替わります。

## 1. 全体像

```
[登録直後]  register.html → 確認コード送信 → コード入力 → セッション発行 → mypage.html
[後日]      mypage.html(未ログイン) → login.html → メール入力 → 確認コード → セッション発行 → mypage.html
[施錠範囲]  mypage.html のみ（LP・相性診断・体験デモ my-tenki-demo.html は今まで通り誰でも閲覧可）
```

- **パスワードは扱いません**（作らない・保存しない）。本人確認は「メールに届く6桁コード」で行います。
- 登録メールの打ち間違いは、**登録直後の確認コードが届かないこと**で即発覚し、`login.html` / `register.html` の「アドレスを直す」導線から正しいアドレスへ送り直せます。

## 3. 本番切り替え（エンジニアの作業）

### 3-1. API ベースURLの設定
各HTML（`register.html` / `login.html` / `mypage.html`）の下記1行に、実装したAPIのベースURLを入れるだけです。

```html
<script>window.UNKIYOHO_AUTH_API_BASE = "https://api.unkiyoho.jp";</script>
```

- 空文字のままなら開発モード（メール未送信・ブラウザ内で完結）。
- URLを入れると、`auth.js` が §4 のAPIを `credentials:'include'`（Cookie付き）で呼び出します。
- **CORS**：APIはこのURL/ドメインからのリクエストを許可し、Cookie を使うため `Access-Control-Allow-Credentials: true` と、`Access-Control-Allow-Origin` に**具体的なオリジン**（`*` 不可）を返してください。同一オリジン配信ならCORS不要。

### 3-2. 必要なもの（Google環境の例）
- サーバー実行環境：**Cloud Run** / Cloud Functions（第2世代）/ Firebase Functions など。
- データ保存：**Firestore**（下記コレクション）または Cloud SQL。OTPは短命なので Firestore/Memorystore(Redis) が手軽。
- メール送信：**送信サービスのAPIキー**（未定なら Resend / SendGrid / Amazon SES 等。`docs` の参考実装に差し込み口あり）。送信元ドメイン `unkiyoho.jp` の **SPF / DKIM** 設定を必ず行う（迷惑メール振り分け・到達率対策）。

## 4. API 仕様（サーバーが実装する4本）

すべて `Content-Type: application/json`。認証はサーバー発行の **HttpOnly / Secure / SameSite=Lax Cookie**（例：`session=...`）で行う。

### 4-1. `POST /auth/request-code` — 確認コードを送る
リクエスト：
```json
{ "email": "user@example.com", "purpose": "login | register | change-email" }
```
処理：
1. `email` を正規化（trim + 小文字化）。形式チェック。
2. **レート制限**（例：同一メール 1分1回・1時間5回／同一IP も制限）。超過は `429`。
3. 6桁コードを生成し、**ハッシュ化して保存**（平文で保存しない）。有効期限10分・試行回数0で記録。
4. コードをメール送信（件名例：「【運気予報】確認コード（10分間有効）」）。
5. **メール列挙対策**：存在しないメールでも成功と同じ `200` を返す（「登録がない」ことを外部に漏らさない）。ただし `purpose:"register"` は登録フロー直後なので存在前提で可。

レスポンス（常に）：
```json
{ "ok": true }
```
> 本番レスポンスにコードを**絶対に含めない**（開発モードのみフロントが自前生成のコードを表示）。

### 4-2. `POST /auth/verify-code` — 検証してログイン
リクエスト：
```json
{ "email": "user@example.com", "code": "483920", "remember": true }
```
処理：
1. 保存済みコードを取得。無ければ `400 {code:"no_pending"}`。
2. 有効期限切れ → `400 {code:"expired"}`。試行回数 +1、上限（5回）超過 → `400 {code:"too_many"}` してコード無効化。
3. ハッシュ照合。不一致 → `400 {code:"invalid_code", remaining: 残回数}`。
4. 一致：コードを使い捨て（削除）。ユーザーが未作成なら作成（`purpose:"register"` 時）。`change-email` 時は既存ユーザーのメールを更新。
5. **セッション発行**：ランダムなセッションIDを保存し、`Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax; Path=/`。
   - `remember=true`（「ずっとログインしたままにする」ON・既定）：長期Cookie（`Max-Age` 例：365日）。**利用のたびに期限を延長（スライディング）** すると、毎日カレンダーを見るユーザーは実質ログアウトされず、コード再入力が不要になります（`GET /auth/session` で延長するのが手軽）。
   - `remember=false`（共用端末など）：`Max-Age` なしのセッションCookie＋短命セッション（例：12時間）で自動失効。

レスポンス：
```json
{ "ok": true, "nick": "あかり" }
```
エラーは上記 `code` を含めて返す（フロントが日本語メッセージと残回数を表示）。

### 4-3. `POST /auth/logout` — ログアウト
- セッションを破棄し、Cookie を失効（`Max-Age=0`）。`{ "ok": true }`。

### 4-4. `GET /auth/session` — 現在のログイン状態（任意だが推奨）
- Cookie を検証し、`{ "loggedIn": true, "email": "...", "nick": "..." }` を返す。未ログインは `{ "loggedIn": false }`。
- フロントの高速な出し分けは localStorage キャッシュで行うが、正となるのはこのエンドポイント。

### 4-5. `change-email` の本人確認（アドレス修正フロー）
- `login.html` の「打ち間違えたので直したい」は、`purpose:"change-email"` で新アドレスへコードを送る際、`identify:{nick, birth}` を同送する想定（`auth.js` の `requestCode` 引数に含める）。
- サーバーは `nick + birth` で既存ユーザーを照合し、一致した場合のみ新アドレスへコード送信 → 検証成功でメール差し替え。**照合できない場合も成功レスポンス**（列挙対策）で、実際には送らない運用でも可。
- マイページの「メール変更」は、ログイン済みセッションで `change-email` を行うため本人確認済み。

## 5. データモデル（Firestore の例）

```
users/{userId}
  email        (string, 正規化済み, ユニーク)
  nick         (string)
  birth_date, birth_time, time_unknown, sex, pref, rel, interests[]  // 既存の登録項目
  mail_opt     (bool)   // 毎朝メールの購読
  consent_at   (timestamp)   // 同意記録（特電法・個情法／消さない）
  created_at, updated_at

otp/{email}            // 短命・TTL自動削除推奨
  code_hash    (string)  // 平文で保存しない
  purpose      (string)
  expires_at   (timestamp)  // 10分
  attempts     (number)     // 上限5
  sent_at      (timestamp)  // 再送クールダウン判定

sessions/{sessionId}
  user_id, created_at, expires_at, remember(bool), user_agent(任意)
```

- 生年月日・時刻は要配慮に準じる個人情報。**保存時暗号化・アクセス制御**を厳格に（仕様書§10.6）。
- 既存の登録受付（`register.html` の `saveEntry` → Googleフォーム or 自前API）と**同じ users レコード**に寄せると二重管理を避けられます。

## 6. セキュリティ要件（必須）

- 🔒 **本当の保護はサーバー側**。`auth.js` の localStorage セッションは画面の出し分け(UX)専用。**マイページの会員データを返すAPIは、必ず Cookie セッションを検証**してから返すこと（クライアント判定を信用しない）。
- OTPは**ハッシュ化保存・10分・5回・使い捨て・再送クールダウン**。
- **レート制限**（メール／IP）でコード送信の乱用・総当たりを防止。
- Cookie は **HttpOnly / Secure / SameSite=Lax**。
- **メール列挙対策**（存在有無を漏らさない）。
- 送信元ドメインの **SPF / DKIM / DMARC**。
- 同意日時・解約記録は**消さない**（法令）。

## 7. 動作確認（いまの開発モード）

1. Webサーバー経由で `register.html` を開く（`python3 -m http.server` など。`file://` 不可）。
2. フォーム送信 → 「あと1歩！メールを確認」画面に、黄色い枠で**確認コードが表示**されます（開発モードのため）。
3. コード入力 → 「メール確認、完了しました！」→ マイページへ。
4. `mypage.html` を新しいタブで開くと、ログイン状態なら表示。ログアウト後に開くと `login.html` に飛ぶ（＝施錠）。
5. `login.html` で同じメールを入れ、表示されるコードで再ログイン。「アドレスを直したい」で送り直しも確認できます。

> 開発モードのコードは、ブラウザのコンソールにも出力されます（`[運気予報:開発モード] ...`）。
