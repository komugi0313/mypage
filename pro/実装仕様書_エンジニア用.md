## 0. 30秒でわかる全体像

- **プロダクト**：四柱推命の自動鑑定ツール（B2B、プロ鑑定者向け）。ブランド **Meishiki Inc.**、月額 **9,800円（税込）**。
- **フロント**：ビルド不要の**静的PWA**（HTML/CSS/JSのみ、フレームワーク無し）。このリポジトリ `pro/` 配下がそのまま本番のフロントです。
- **あなたが作るもの**：下記 **7本のHTTP API**（サーバーレス関数）＋ **決済（テレコムクレジット）**＋ **本番フラグの切替**。ホスティング先は **Google（Cloud Run / Cloud Functions 等）想定**でOK。

### 全体構成図

```
[ブラウザ / PWA / 将来はアプリ ]
        │
        │  fetch( <API_BASE>/<関数名> )  ※フロントは既定で相対パス /.netlify/functions/*
        ▼
[ あなたのサーバー（Google） ]  ←─ サーバーレス関数 7本
        ├─ 認証・会員（メール＋パスワード、契約ステータス管理）
        ├─ マイページ同期（鑑定者=顧客カルテの保存/読み込み）
        ├─ Gemini 中継（APIキーはサーバーが保持）
        └─ 決済（テレコムクレジット）で契約ステータスを更新
```

> **API_BASE について**：フロントの各ファイルは既定でパス `'/.netlify/functions'` を使っています（Netlify 名残の定数名ですが、**中身は「あなたのAPIのベースパス」という意味**です）。Google 側で `/.netlify/functions/<関数名>` に同じ関数を割り当てる（リバースプロキシ/リライトでOK）か、または後述の**定数を1か所ずつ書き換えて**別ベースURLに向けてください。どちらでも動きます。

## 3. サーバーAPI仕様（作るのはこの7本）

- 通信は全て **HTTPS / `POST` / `Content-Type: application/json`**（Gemini 中継のみ Google の generateContent 形式をそのまま透過）。
- フロントの既定ベースパスは `'/.netlify/functions'`。関数名は下表のパス末尾。
- **CORS**：同一オリジン配信ならなくても可。別オリジンなら適切に許可。
- 認証方式は現状 email＋password をフロントが `localStorage` に保持して都度送る簡易方式です。**セキュリティ強化として、ログイン成功時にセッショントークン（JWT等）を返し、以後はトークンで認証する方式に切り替えることを推奨**（§8参照）。現行フロントを動かすだけなら下表の契約を満たせば足ります。

### 3-1. 認証・会員（4本）

呼び出し元：`auth.html`（登録/ログイン/パスワード再設定画面）と `app-pro.html`（起動時のログインゲート）。

| 関数（パス末尾） | メソッド | リクエスト body | 成功レスポンス | 失敗 | 役割 |
|---|---|---|---|---|---|
| `auth-register` | POST | `{ email, password }` | `{ ok:true }` | `{ ok:false, error }` | 新規会員登録。確認メール送信。**この時点では未課金**（status=`none` 相当） |
| `auth-login` | POST | `{ email, password }` | `{ ok:true, status, email }` | HTTP 401 または `{ ok:false, error }` | ログイン。**契約ステータスを必ず返す**（下記の値） |
| `auth-verify` | POST | `{ token }` | `{ ok:true, email }` | `{ ok:false, error }` | 確認メールのリンク検証 |
| `auth-reset` | POST | `{ email }` | `{ ok:true }` | `{ ok:false, error }` | パスワード再設定メール送信 |

**`status`（契約ステータス）の値**（フロントの `statusJa()` が対応済み）：

| status | 意味 | アプリ解錠 |
|---|---|---|
| `active` | 課金中 | **解錠する** |
| `trialing` | 無料トライアル中 | **解錠する** |
| `past_due` | 支払い遅延 | しない |
| `canceled` | 解約済み | しない |
| `unpaid` | 未払い | しない |
| `none` | 未契約 | しない |

- フロントのゲート判定（`app-pro.html` 663〜675行付近）：`auth-login` の応答が `status==='active' || status==='trialing'` のときだけ `unlock()`。それ以外は課金導線へ誘導。
- ログイン情報は `localStorage` に `member_email` / `member_pw` / `member_remember` として保存され、起動時に自動再ログインを試みます。**トークン方式に変える場合は §8 の注記に従い、フロントの該当箇所も併せて調整**してください。

### 3-2. マイページ同期（2本）

呼び出し元：`app-pro.html`（顧客カルテ＝鑑定した相手の保存）と `mypage-pro.html`。ログイン中（`member_email` あり）のときだけサーバー同期。未ログイン/未デプロイ時は端末内 `localStorage` のみで動作します（フロントがフォールバック済み）。

| 関数 | メソッド | リクエスト body | 成功レスポンス | 役割 |
|---|---|---|---|---|
| `mypage-get` | POST | `{ email }` | `{ data: <ドキュメント> }` | そのユーザーの保存データを取得 |
| `mypage-put` | POST | `{ email, data: <ドキュメント> }` | `{ data: <保存後のドキュメント> }` | 保存（サーバー側で後述のマージを推奨） |

**ドキュメント形式**（`data`）：

```json
{
  "schema": 2,
  "updatedAt": 1727600000000,
  "clients": [
    {
      "id": "一意ID",
      "name": "顧客名",
      "ts": 1727600000000,
      "deleted": false
      /* 以下、鑑定メモ・保存した命式など任意フィールド */
    }
  ]
}
```

- フロント側キー：`DKEY='bazi_mypage_v2'`、旧 `CKEY='bazi_clients_v1'`。`clients[]` の各要素は `ts`（更新時刻）と `deleted`（論理削除フラグ）を持ちます。
- **マージ推奨**：`mypage-put` はクライアントとサーバーの `clients[]` を **`id` 単位で `ts` の新しい方を採用**して統合すると、複数端末でも安全（片方向上書きだと消えます）。`deleted:true` は墓石として保持。

### 3-3. Gemini 中継（1本）

呼び出し元：`app-pro.html` の詳細鑑定（生成鑑定文）。**APIキーは絶対にフロントに出さず、サーバーが環境変数で保持**します。

| 関数 | メソッド | 役割 |
|---|---|---|
| `gemini` | POST | フロントから来た Gemini `generateContent` 形式の body を、サーバー保持の `GEMINI_API_KEY` を付けて Google に中継し、応答をそのまま返す |

- フロントが送る body（そのまま Google の `generateContent` に渡せる形）：

```json
{
  "system_instruction": { "parts": [ { "text": "…システム指示…" } ] },
  "contents": [ { "role": "user", "parts": [ { "text": "…ユーザー入力…" } ] } ],
  "generationConfig": { "maxOutputTokens": 2048, "thinkingConfig": { /* … */ } }
}
```

- 任意ヘッダ **`x-pk-deep: 1`**：詳細（深め）鑑定の指定。サーバーは受け取ったら思考量を増やす等の分岐に使ってOK（無視しても動作はします）。
- 中継先モデル：既定 **`gemini-2.5-flash`**（URL 例：`https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent?key=<GEMINI_API_KEY>`）。
- **タイムアウト/圏外時**：フロントは約5秒でサーバー応答が無ければ**端末内オフライン鑑定に自動フォールバック**します。サーバーは通常の JSON を返せば十分。
- レスポンスは Google の `generateContent` 応答 JSON をそのまま返却（フロントが `candidates[].content.parts[].text` を読みます）。

## 4. 決済（テレコムクレジット）

- **プラン（`pricing-pro.html` の `PLAN` 定義、税込）**：

  | キー | 表示価格 | 更新 |
  |---|---|---|
  | `month` | **9,800円** | 1か月ごと |
  | `half` | **52,800円** | 半年ごと |
  | `year` | **98,000円** | 1年ごと |

- **無料トライアル**：**メール＋クレジットカード登録で7日間無料**。トライアル中は `status=trialing`（アプリ解錠）。7日経過で自動的に本課金 → `active`。
- **決済URL**：`pricing-pro.html` の `TELECOM_PAYMENT_URL = { month:'', year:'', half:'' }` は現在**空**。空のあいだは画面に「ただいま決済ページの接続を準備中です」と出て、課金導線は無効（安全）。**テレコムクレジットの審査通過後、各プランの決済URLを設定**してください。
- 決済完了 → テレコムクレジットからの通知（Webhook/戻りURL）を受けて、**会員の `status` を `active`/`trialing` 等に更新**するのがサーバーの役目。フロントは次回ログイン時の `auth-login` 応答 `status` を見て解錠します。
- **不正トライアル対策（推奨）**：同一カード指紋・同一端末での無料トライアル再取得をサーバー側で弾く。メールだけの重複登録では無料が無限に取れないよう、**カード登録を必須**にしている前提です。
- 特商法・規約は同梱済み：`tokushoho-pro.html`（販売事業者/所在地/電話/価格/支払方法/解約を記載）、`terms-pro.html`、`privacy-pro.html`。**事業者情報・ドメインは実データに要差し替え**。

## 8. セキュリティ必須事項

1. **`GEMINI_API_KEY` はサーバーのみ**。フロントの `gtest-wrap` テストキー欄は本番で削除（§2 #3）。
2. 全通信 **HTTPS**。パスワードは **ハッシュ保存**（bcrypt/argon2 等）。
3. **推奨：セッショントークン化**。現行は `email+password` を都度送る簡易方式。ログイン時に短命トークンを発行し、`mypage-*` などはトークンで認可する方式に。移行時はフロントの `member_pw` 保存箇所（`app-pro.html` ゲート／`auth.html` CONFIG）も併せて更新。
4. `auth-*` はレート制限・総当たり対策を。`auth-verify`/`auth-reset` のトークンは短命・ワンタイム。
5. 決済通知（テレコムクレジット Webhook）は**署名検証**して `status` を更新。

## 10. Web の次：iOS / Android アプリ化

- 方針：**Web優先（テレコムクレジット）で先行公開 → のちにネイティブアプリ**。
- `app/` に **Capacitor スキャフォールド**（`capacitor.config.json` / `package.json` / `scripts/` / `README.md`）あり。**`pro/` の Web をそのままラップ**する構成。
- **重要（審査対応）**：**iOS/Android アプリ内でデジタル課金する場合、Apple/Google は原則ストア内課金（IAP）を要求**します。アプリ版では課金経路をストアIAPに切り替える／またはガイドラインに沿った導線設計が必要。**Web（テレコムクレジット）とアプリ（IAP）で決済が分岐する**点を初期設計に織り込んでください（`status` 管理はサーバー共通、決済プロバイダだけ分岐）。
