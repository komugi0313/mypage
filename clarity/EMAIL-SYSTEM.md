# Numinous — 毎朝の手紙（Daily Letter）配信システム 設計メモ

日本の「運気予報」型のリテンションを、米国向け Numinous に載せるための設計書。
無課金勢を「毎朝の手紙」で繋ぎ止め、有料（Pro）はアプリ全機能＋カレンダーで差別化する。

---

## 0. いちばん大事な前提（技術的な現実）

**今の Numinous は「サーバーを持たない静的サイト」です。** データは全部ブラウザの
`localStorage`（＝その端末の中）に入っているだけで、外に送られていません。

- メールアドレスも、名前も、性別も、今はどこにも「保存」されていない
- だから **今のままでは1通もメールを送れません**

「毎朝あなただけのメールを送る」を実現するには、最低限これが必要です：

1. **登録者データベース**（メール・チャート・プロフィール・購読状態を保管する場所）
2. **メール送信サービス**（Postmark / SendGrid / Amazon SES など。自前のGmailでは無理）
3. **毎朝動く仕組み（スケジューラ / cron）**（各人のチャート×その日の運気で本文を生成して送る）
4. **配信停止（unsubscribe）と法令対応**（米国 CAN-SPAM は「送るなら義務」）

→ ここは「LPに一文足す」より一段大きい開発です。順番は §6 の3フェーズを推奨。

## 1. 「トライアル時に属性を聞くのは失礼か？」への結論

**失礼ではない。ただし “必須にする” と失礼（＆離脱）になる。** 米国では特に。

米国ユーザーは、性別・出身国・人種・年齢を**必須で**聞かれると
「なぜ要る？差別に使う気か？」と身構えます（雇用・与信の文脈を連想するため）。
でもパーソナライズ product では、下記3点を守れば全く問題なく、むしろ喜ばれます。

- **すべて任意（skip可）** — 空でも登録・配信できる
- **理由を一言そえる** — “to make your morning letter truly yours”
- **表現をインクルーシブに** — 特に性別

### 具体的な聞き方（推奨）

| 項目 | 推奨 | 理由 |
|---|---|---|
| 名前 | **ニックネームでOKと明記** `What should the letter call you?` | 本名を強制しない。手紙の宛名に使うだけ |
| 性別 | 任意・選択式：`Woman / Man / Non-binary / Prefer to self-describe ⌨︎ / Prefer not to say` | 米国標準のインクルーシブ表記。M/Fの2択だけは今の米国では古い |
| 年代 | **聞かない**（生年月日から自動算出） | 既に誕生日を取得済み。二重に聞くと不信 |
| 属性/仕事 | 任意・ゆるい選択：`Founder / Executive / Professional / Creative / Student / Other` | LPのターゲットに沿う。自由記述より負担が軽い |
| 住まい | **「出身国」より「今住んでいる都市／タイムゾーン」** | 配信時刻（毎朝5時＝現地時間）に実際に必要。出身国は聞く実用理由が薄い |
| 出身国 | 任意。聞くなら “where you’re from (optional)” と最後に | 必須にしない。無くても配信は成立する |

**要点：** 誕生日・出生地は「鑑定に必要」だから既に必須で聞けている。
今回追加する属性は「手紙をあなた宛てにするため」。この線引きを画面で言葉にすると
「なぜ聞くのか」が伝わり、失礼になりません。

## 2. 無料 / 有料（Pro）の線引き

ユーザー方針（＝この設計の基準）：

- **メール（毎朝の手紙）… 無料も有料も同じ内容・全員受け取れる**
- **カレンダー … 無料は見れない（Pro限定）**

推奨する最終形：

| | 無料（トライアル終了後） | Pro（有料） |
|---|---|---|
| 毎朝の手紙（メール） | ✅ 届く | ✅ 届く（同じ内容） |
| 自分のチャート閲覧 | ✅（基本） | ✅（フル） |
| 「なんでも質問」readings | 体験のみ / 制限 | ✅ 無制限 |
| 日次カレンダー | ❌ 見れない | ✅ 全月 |
| 総合診断・深いI Ching | ❌ | ✅ |

**補足（転換率のコツ）：** 手紙の末尾に
「Today is a 🌈 tailwind day for you — see the whole month in the calendar → (Pro)」
のように、**その日の手紙からカレンダー（Pro）へ**の動線を1本入れると、
無料で満足しつつ課金理由が毎朝伝わります。

### 実装メモ（entitlement）
今のコードは `isPro()`（`localStorage['clarity_pro']==='1'`）で
「Pro＝全カレンダー / それ以外＝2ヶ月」を出し分けている（app.html 1578行あたり）。
「無料はカレンダー**ゼロ**」にするには、状態を3つに増やす必要がある：

- `trialing`（トライアル中：現状どおり2ヶ月見せてよい）
- `free`（トライアル終了・未課金：カレンダータブを丸ごとロック＝Proへ）
- `pro`（課金中：全月）

この3状態は**サーバー側の購読状態**が正なので、§3のバックエンドと一緒に実装する。
（フロントだけで判定すると、いくらでも回避できてしまうため。）

## 3. データモデル（登録者DB）

送信サービスに何を渡すかの最小セット。DBでもESPのカスタムフィールドでも同じ。

```
subscriber
  id                 uuid
  email              string   (必須・検証済みか)
  email_verified     bool     (double opt-in 済みか)
  status             enum: pending | active | unsubscribed | bounced
  plan               enum: trialing | free | pro | canceled
  # 手紙を宛先化＆本文生成するための情報
  nickname           string?  (宛名。無ければ "there")
  gender             string?  (自由記述可)
  role               string?  (Founder 等)
  # 配信に実用的な情報
  timezone           string   (例 "America/Los_Angeles" — 毎朝の送信時刻に必須)
  send_hour          int      (全員 5 = 現地時間の朝5時に統一。ユーザー選択なし)
  # 鑑定エンジンの入力（既存 clarity_birth と同じ）
  birth_date         date
  birth_time         time?
  birth_place        string?  (true solar time 用)
  # 任意
  country_of_origin  string?
  created_at, updated_at
  unsubscribe_token  string   (推測不能・1人1つ)
```

チャート（favorable element 等）は毎朝 `meishiban_pillars.html` の計算ロジックを
サーバー側に移植 or 呼び出して算出する。誕生日から決まる固定値なので保存キャッシュも可。

## 4. 毎朝の配信フロー（cron）

```
毎時0分に起動（タイムゾーン差を吸収するため1時間毎に回す）
 └ 「今この時刻が現地 send_hour の人」を抽出（status=active かつ email_verified）
     └ 各人ぶん:
         1. その人のチャート × 今日の日運（DayFortune 相当）を計算
         2. 本文テンプレに差し込む（宛名＝nickname、favorable element、今日のランク/色/一手）
         3. 送信サービスにPOST（unsubscribe ヘッダ＆リンク必須）
         4. 送達/バウンス/開封を記録（バウンス続きは status=bounced に）
```

**本文トーン（占いに見せない）：** 「lucky/fortune/horoscope」を避け、
"a quiet piece of counsel for your day" の言い回しで。件名例：
`Your morning, <nickname> — a tailwind day` / `<nickname>, one move that fits today`

## 5. 米国で「送るなら必須」の法令・お作法（CAN-SPAM ほか）

メールを送る以上、これは"やった方がいい"ではなく**義務／必須運用**：

1. **配信停止リンクを全通に**（1クリックで、10日以内に反映）
2. **差出人・実在住所を明記**（footerに 72k Inc. の住所）
3. **件名を偽らない**（釣り件名NG）
4. **double opt-in 推奨**（登録後に確認メール→クリックで active）。誤登録・なりすまし・
   到達率悪化を防ぐ。無料メインの設計なら特に効く
5. **プライバシーポリシー更新**（何を集め・何に使い・第三者提供の有無）。
   性別・出身国など**センシティブ属性を集めるなら明記必須**。
   米国はカリフォルニア（CCPA/CPRA）も要考慮
6. **未成年除外**（LP既に 18+ 表記あり。登録時も確認）

※ 決済は Apple IAP＋Google Play課金に決定（§8）。購読状態は Apple / Google からの
   購入通知が正となり、§2の3状態（trialing/free/pro）はこれと同期する。

## 7. アカウント／ログイン（決定事項）

**アプリのログインは「メールアドレス＋パスワード」に決定（2026-07-31）。**
メールは配信の宛先であると同時にアカウントのIDになる。1アカウント＝
「毎朝の手紙の宛先」＋「アプリの購読状態（trialing/free/pro）」を束ねる。

実装要件（エンジニア向け・必須）：

1. **メール実在確認はダブルオプトインと兼用** — 登録時の確認メールクリックで
   `email_verified=true`。未確認のアドレスには手紙を送らない（§4のとおり）。
   これにより「正しいメールアドレスでなければ配信されない」が仕組みで担保される。
2. **パスワードは平文保存禁止** — bcrypt または argon2 でハッシュ化。
   最低8文字。ログイン試行はレート制限（総当たり対策）。
3. **パスワード再設定** — 「Forgot password?」→ 登録メールに再設定リンク
   （期限付きトークン）。メールが受け取れる＝本人確認になる設計。
4. **セッション** — サーバー発行のトークン（JWT等）。購読状態（trialing/free/pro）は
   常にサーバーが正（§2の3状態と同期。フロント判定だけでは回避されるため）。
5. **アプリ内でのアカウント削除** — Apple審査ガイドライン5.1.1(v)により、
   アカウント作成があるアプリは「アプリ内から削除」できることが必須。
   削除時は配信も自動停止。
6. **ソーシャルログインは入れない**（重要な割り切り）— Google/Facebookログイン等を
   足すと、Appleの規約で「Sign in with Apple」の併設が義務になる。
   メアド＋パスワードのみなら、その義務は発生しない。将来足すなら同時対応が必要。
7. **既存ユーザーの移行** — 現状のlocalStorage利用者には、次回起動時に
   「アカウント作成（メール＋パスワード）」を案内し、端末内のチャートを引き継ぐ。

データモデルへの追加（§3のsubscriberに追記）：
```
  password_hash      string   (bcrypt/argon2。平文・可逆暗号は禁止)
  password_reset_token / expires  (再設定用・期限付き)
```

## 8. 意思決定ログ

- **配信基盤：B（自前バックエンド）に決定（2026-07-17）** — 創業者のエンジンで
  1人ずつ本文を生成するため。実装は `server/`（README参照）。無料枠は認知獲得
  チャネルと位置づけ、100〜200万人規模で広告枠（`server/src/ads.js`）を収益化する。
- **アプリのログインはメールアドレス＋パスワードに決定（2026-07-31）** — §7参照。
  メール実在確認はダブルオプトインで担保（正しいメアドが無ければ配信されない）。
- **決済：第1弾は Apple IAP＋Google Play課金に決定（2026-07-31）** — 米国向け・
  アプリのみ（Webなし）のため、外部決済用のWebページを持たない構成を優先。
  手数料は原則30%・年間売上100万ドル以下は15%（App Store Small Business Program /
  Google Play 15% Program に**両方とも申請すること**。自動適用ではない）。

  エンジニア向け実装要件：
  1. **購読状態の"正"はストアからのサーバー通知** — Apple: App Store Server
     Notifications V2 / Google: Real-time Developer Notifications (RTDN)。
     サーバーがこの通知を受けて subscriber.plan（trialing/free/pro）を更新する。
     アプリ内のレシートだけで判定しない（改ざん・失効ズレの元）。
  2. **無料トライアルはストアのIntroductory Offer / Free Trial機能で実装**し、
     期間・自動更新の文言はストア規約どおり購入画面に明示する。
  3. **購入の復元（Restore Purchases）ボタン必須**（Apple審査要件。機種変更・
     再インストール時にProを復元する）。
  4. **解約導線** — 解約はストアの購読管理画面に委ねられる。アプリ内に
     「Manage subscription」リンク（各ストアの購読設定へ飛ぶ）を置く。
  5. アカウント（メール＋パスワード）とストア購入の紐付けは、購入時の
     appAccountToken（Apple）/ obfuscatedExternalAccountId（Google）にサーバー発行の
     ユーザーIDを入れて行う。これで「どのメールの人がProか」がサーバーで確定し、
     メール配信・カレンダー解放と連動する。
  6. 将来Web版を復活させ外部決済を併用する場合も、購読状態はサーバー正のまま
     通知源（ストア通知 / 決済代行Webhook）が増えるだけの設計とする。

- **配信時刻：全員「現地時間の朝5時」に統一（2026-07-31決定）** — ユーザー選択なし。
  実装は既存の毎時cron方式のまま（毎時0分に起動し「いま現地5時のタイムゾーンの人」に
  送る）。send_hour の既定値を 5 に変更済み（db.js / server.js）。
  ※「統一」は各自の現地時刻での統一。世界同時刻の一斉送信にすると地球の裏側では
  深夜着になるため、「誰にとっても朝5時」がこの決定の意味。
- **配信国：全世界に決定（2026-07-31）** — App Store / Google Play の配信地域を
  全世界に設定。命式計算は節気＝天文基準の国際標準方式のため、**南半球生まれも
  月支を反転させず同方式で正しく算出する**（主流派の立場。真太陽時・日付跨ぎ対応済み）。価格は基準額のみ設定し、各国通貨への換算・税の徴収はストアに委ねる。
  ※注意：中国本土のApp Storeは占い・運勢系に政府許認可が必要なため、審査却下や
  掲載後削除があり得る。問題が起きた場合は配信地域から中国本土のみ除外して対処。
  EU配信に伴い、プライバシーポリシーにEU居住者の権利（GDPR）の節を追加すること
  （同意証跡・アカウント削除・データ閲覧/消去は実装済みのため追記のみで足りる）。

- **日評価に流年・流月を実装（2026-07-31）** — 日々の採点（dayfortune.js＝手紙と
  アプリのカレンダー共通）に「その年の柱・その月の柱」を追加：①月令（月支の季節が
  その日の五行を旺じるか）②歳破・月破（日と年支/月支の冲）③日＋流年/流月＋命式で
  完成する三合。これにより同じ干支の日でも年が替われば約24%、月が替われば約35%が
  別の評価になり、文面の繰り返し周期が構造的に消えた（テンプレ版でも720日間で
  完全一致ゼロを実測）。手紙の根拠枠にも「この鑑定は◯◯月・◯◯年の流れの中で
  読んだもの」と明記される。実装後、公式smokeテスト・8人×120日の古典ルール照合・
  ブラウザ動作（エラー0）をすべて再検証済み。
- **手紙の生成：AI生成に決定（2026-07-31）** — 流れ：登録時の誕生日・出生時刻・
  出生地から命式をサーバーで自動作成（engine-full.js＝本物の鑑定エンジンを
  ヘッドレス実行）→ 毎朝、その人の命式×当日の日運から「事実」を算出 →
  AI（coach-ai.js）がその事実だけをコーチング調の英文に書き上げて送信。
  実装済み。本番では環境変数 LETTER_AI=1 と GEMINI_API_KEY（サーバー側のみ・
  フロントに出さない）を設定して有効化する。

  安全設計（実装済み・変更しないこと）：
  1. **AIは事実を発明できない** — エンジンが計算した値（日運ランク・十神・
     エネルギー・注意フラグ等）だけを渡し、「数字・方角・新しい主張の追加は禁止」
     とプロンプトで固定。法務フッターと配信停止リンクはAIを通さずコードで付与。
  2. **AI障害時は自動でテンプレ版に切替** — Geminiが落ちても配信は止まらない。
  3. **コストは購読者数に比例しない** — 本文は「状況（命式×その日）」で決まるため
     状況ハッシュでキャッシュし、同じ状況の数千人分を1回の生成で賄う。
     1日の生成回数は状況の組合せ数で頭打ちになり、gemini-2.5-flash なら
     月額数ドル規模で50万人にもスケールする。
  ※性質上、同じ状況の人には同じ文面が届く（事実は各自の命式由来なので
  「自分の鑑定」として成立する）。宛名はニックネームで個別化される。
