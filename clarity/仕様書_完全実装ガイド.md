## 0. 最重要原則（先に読んでください）

1. **占術エンジンのファイルは書き換え禁止。**
   `bazi.js` / `dayfortune.js` / `cycles.js` / `geo.js` / `meishiban_pillars.html` が計算の正典。アプリ表示・メールの手紙・カレンダーの吉凶はすべてこの同一ファイル群から計算されます。移植が必要でも**逐語的に抽出**し、ロジックの書き換え・「改善」は絶対にしない。計算が1つずれると商品全体の信用が消えます。
2. **`bazi-bridge.js`（エンジン読取り部品）も書き換え禁止。**
   この部品はアプリとサーバーの両方が使い、§4の実機不具合をすべて吸収した現在の形が完成形です。1行の「clean up」が iPhone 全滅を再発させます。変更が避けられない場合は §10 の全テストを必ず通すこと。
3. **APIキー・ベンダー名は表に出さない。**
   言語生成のAPIキーはサーバーの `.env` のみ。クライアント・リポジトリ・コミット・配布物には一切含めない。UI/LP/規約からベンダー名（Gemini等）は除去済み——この状態を維持する。
4. **鑑定は engineExact ゲートを通ったチャートからのみ生成。**
   アプリは完全エンジンの確定値が取れるまで鑑定文を書きません（`requireExactChart`）。サーバーも登録時にエンジンが失敗したら503を返し、誤ったチャートを保存しません。この安全装置を外さない。

## 3. 計算エンジン仕様（正確性の要）

実装済み・検証済み。エンジニアが新規に書くものはありませんが、**何が保証されているか**を理解してデプロイ検証に使ってください。

- **真太陽時**: `Geo.correct(date,time,lon,utcOffset,dst)` が経度差＋均時差で補正。日付跨ぎは `dayShift` で日柱も移動。160都市内蔵、南半球含む全世界対応。
- **夜子時**: 23時台生まれは日柱=当日のまま、時柱のみ翌日の日干基準。
- **日運**: `DayFortune.dayFortune(chart,y,m,d)` — 7段階。用神生剋・三合/六合/干合/天地徳合・貴人・桃花・冲・空亡・神殺・十二運＋**流年流月**（月令/歳破/月破/三合完成）。同じ日干支でも年月で評価が変わる（実測: 年24%・月35%変動）。
- **大運・流年**: `Cycles.build(...)` — 10年チャプター・節木運・三合/方合成立年・墓庫開冲・駅馬。

**受け入れアンカー値**（デプロイ後に必ず照合）:

| 入力 | 期待値 |
|---|---|
| `npm run verify:engine`（server/） | 全項目PASS（JDN・日柱外部アンカー・6000日連続性・夜子時23:59境界・真太陽時日付跨ぎ・大運男女順逆・二重補正ガード） |
| 1985-07-20 14:30 女性 New York | 日主 **庚**・**身強**・用神 **Water**・月支元命 **印綬**・大運 **丁亥** 2021–2030 |
| 2000-01-01 | 日柱 **戊午** |

## 4. 実機で踏んだ地雷と再発防止ルール（必読）

以下は**すべて実機（iPhone実機・Netlify実デプロイ・実メール送信）で実際に発生した不具合**です。現在のコードはすべて修正済み。各項目の「ルール」を破ると再発します。

### 地雷1：メール配信が全世界に届かない（致命）
- **症状**: 配信は動いているのに、サーバー所在地の朝5時の地域にしか届かない。
- **原因**: 配信対象の絞り込みが「サーバーの現在時刻」基準だった。全員 send_hour=5 のため、サーバー時刻が5時台の1時間しか対象が発生しなかった。
- **修正**: `send.js sendDue()` — 通常実行は **active全員を走査し「本人のタイムゾーンの現在時刻 == 本人のsend_hour」** で判定。`--hour N` は時計無視の強制送信（テスト/バックフィル用）に意味を変更。
- **ルール**: `sendDue` の判定を「サーバー時刻で dueByHour」に戻さない。**リリース前に §10 の3タイムゾーンテストを必ず実行**。

### 地雷2：iPhoneで命式が永遠に確定しない（致命・最難関だった）
- **症状**: PC では動くのに、iPhone（Safari/Chrome とも中身は WebKit）では常に「We're still computing your exact chart」の赤文字で止まる。
- **原因は3つ重なっていた**:
  1. **起動タイミング**: エンジンページは重く、計算ボタン(f-go)は**DOM上に見えてもクリック動作の配線は初期化の最後**。遅い端末では「ボタンはあるが配線前」の瞬間に自動操作してしまい、何も起きない。旧実装は4回で恒久的に諦める設計だった。
  2. **縦書き問題**: エンジンは画面幅560px以下で縦書きレイアウトに切替わる。隠しiframe（旧: 幅2px/display:none）は常に「狭い」。**iOSのWebKitは縦書きテキストを1文字ずつ改行して返す**ため、「日主」が「日\n主」に泣き別れて読取り正規表現が失敗（診断結果: 強弱=strong は読めるのに 日主=null）。
  3. **保存状態の競合**: エンジン初期化は起動時にデモ命式を描画し、遅い端末では自動操作の**後から**設定を上書きすることがある（二重補正→棄却）。
- **修正**（すべて実装済み）:
  - bridge は f-go の**onclick が関数になるまで**待つ（最大30秒）
  - 設定値（f-corr='none' 等）は**書き込み→待機→定着確認**を繰り返してから実行
  - 読取りは通常テキストと**全空白除去テキストの両方**に対して照合（縦書き泣き別れ対応）
  - 日主は最終手段として `baziCompute()`（純JS・レイアウト非依存）の日柱から復元
  - 再試行は12回・間隔漸増、**鑑定ボタン押下でも再起動**（恒久的に諦めない）
  - iframe は `position:fixed; width:800px; height:640px; opacity:0.01; left:-99999px; pointer-events:none`（幅800px＝縦書き回避）
- **ルール**: **iframe のスタイルと bazi-bridge.js を変更しない**。display:none に「戻して整理」しない、幅を縮めない、待ち時間を「高速化」しない。QA は必ず**実機の iPhone** で行う（シミュレータ/PCでは再現しない）。

### 地雷3：画面が勝手に先頭へスクロールする
- **症状**: 利用中、ページがときどき勝手に一番上へ戻る。
- **原因**: エンジンは計算のたびに自分の結果へ `scrollIntoView` を発行する。iframe が通常フロー配置（absolute）だと**親ページまで巻き込んでスクロール**する。加えて、エンジン再試行のたびに画面を再構築していたことも寄与。
- **修正**: iframe を `position:fixed`（fixedへのスクロールは発生しない）＋再構築時にスクロール位置を保存・復元。
- **ルール**: iframe の `position:fixed` を変えない。`computeChart` 内のスクロール保存・復元を消さない。

### 地雷4：ブラウザのページ翻訳で計算が壊れる
- **症状**: Google翻訳などでページを翻訳して使うと、命式が確定しない。
- **原因**: bridge はエンジンの**日本語の文面**（「身強」「日主」…）を読み取る。翻訳はその文字を書き換える。
- **修正**: `meishiban_pillars.html` に `<meta name="google" content="notranslate">` + `<html translate="no">`、iframe にも `translate="no"`。赤文字メッセージに「翻訳をオフにしてください」の英語案内を追加。
- **ルール**: これらの notranslate 指定を削除しない。

### 地雷5：デプロイの取り違え（Netlify）
- **症状**: 修正版を配ったのに直らない／診断ページが404。
- **原因**: Netlify のトップページにドロップすると**毎回新しいURLのサイトが作られる**。古いURLを開き続けると古い中身のまま。また、フォルダの一部ファイルだけを選んでドロップすると必須ファイルが欠ける。
- **ルール**:
  - 更新は **app.netlify.com → 対象サイト → Deploys タブにドロップ**（URL据え置き）
  - ドロップは**必ずフォルダごと**（`meishiban_pillars.html` が欠けると全鑑定が止まる）
  - **公開サイトには公開用ファイルのみ**を置く。`EMAIL-SYSTEM.md`・`server/`・`HANDOFF.md`・本仕様書などの**内部文書を公開サイトに絶対に置かない**（URLを知られたら誰でも読める）
- 本番はストア配布アプリ（ファイル同梱）なのでこの問題は起きないが、デモ/検証環境では毎回意識すること。

### 地雷6：「答えが出ない」の誤診
- 赤文字には2種類ある。**必ず区別する**:
  - 「We're still computing your exact chart…」= エンジン未確定（§4-地雷2の系統）
  - 「Readings aren't available yet…」= **APIキー未設定なだけ**（デモはURLごとにキー保存。プロキシ本番では出ない）
- **ルール**: 障害切り分けは推測せず、同梱の **engine-check.html** を開かせる（1分で各段階の✅/❌と原因が画面に出る。サポートフローに組み込むこと）。

## 5. アプリのファネルと課金

- **ファネル**（`gateReading()` が一元制御）: 無料鑑定2回（`FREE_READS=2`）→ メール登録ゲート → カード登録 → **3日間無料トライアル** → 4日目から自動課金。
- **フェアユース**（`dailyCap()`）: トライアル/Pro=30回/日、他5回/日。プロキシモードではサーバーが429で強制。
- **課金は Apple IAP + Google Play 課金のみ**（決定事項）。現状の `isPro()`/`trialActive()`/`startTrial()` はデモ層（localStorage）。ストアビルドではレシート検証に差し替え（この3関数に集約済み）。購読状態をサーバーへ反映する場合は IAP Webhook から `db.setPlan(id,'pro')`。

## 6. アプリ実装・設定（エンジニアが実際に触る箇所）

### 6.1 AIプロキシへの切替（必須・リリース前）
`app.html` の設定定数（1か所）:
```js
const BACKEND = { USE_PROXY: false, PROXY_BASE: '' };
// → USE_PROXY: true, PROXY_BASE: 'https://api.numinous.app'
```
trueにすると開発用キー入力欄が消え、鑑定は `POST /api/reading` / `/api/chat` 経由になり、**鍵もモデル名もクライアントに存在しなくなる**。

### 6.2 手紙申込フォームの接続（必須）
```js
const LETTERS = { BASE: '' };   // → 'https://api.numinous.app'
```
未設定/障害時は localStorage に保留→次回起動時に自動再送（ユーザーにはエラーを見せない）。

### 6.3 言語生成モデル（変更不要）
- **`gemini-2.5-flash` にピン留め**（`-latest` は `thinkingBudget:0` 拒否モデルに化けて全滅した実績があるため禁止）。
- `generationConfig`: `maxOutputTokens:2000（chat 1200）, temperature:0.85, thinkingConfig:{thinkingBudget:0}`。60秒×3回リトライ。
- 変更はサーバー `.env` の `GEMINI_MODEL` でのみ行う。

### 6.4 表示の防衛層（維持すること）
- `stripMarks()`: AI出力の漢字用語漏れを平易な英語へ置換（オフライン鑑定だけは `keepCJK` で漢字＋英語説明を保持——混同しない）。
- `screenQuestion()`: 自傷・他害・犯罪は生成前にブロックし相談先（US 988等）を案内。

### 6.5 アプリ化（Capacitor）
`mobile/README-MOBILE.md` 参照。`./build-www.sh` → `npx cap add ios/android` → `npx cap sync`。審査回答集は `store/privacy-answers.md`。**アプリ版はファイル同梱なのでオフラインでも常に起動する**（Webデモとの違い）。

## 8. オフライン鑑定（実装・実機検証済み）

ネット/生成APIに到達できない場合、エラー文ではなく**端末内で命式から合成した英語鑑定**を表示。5機能すべて対応。

- **発動条件** `offlineEligible(err)`: ネットワーク/サービス障害→オフライン鑑定。フェアユース上限と再サインイン要求はそのまま表示。
- **表示**（必ず先頭に赤枠太字バナー）: 「📴 OFFLINE READING — this is NOT the online AI reading」＋「**Even offline, your calculations are still correct.**」
- **内容**: lexicon の解釈値＋エンジン実計算（強い日・避ける日の実日付、用神、大運、当年の十神トーン）。**漢字は必ず英語説明付き**（例: 用神 (yōjin — the one element that steadies your whole chart)）。
- **誠実性**: ユーザーの質問文への個別回答は書かず「接続後に同じボタンを」と明記——オンラインの答えと矛盾しない構造。
- **重要**: オフライン鑑定も engineExact ゲートの**後**にある。エンジンが確定できない端末ではオフライン鑑定も出ない（正しい仕様）。
- **検証手順（実機）**: ①オンラインで開き命式表示を確認 → ②アプリを開いたまま機内モードON → ③質問して鑑定ボタン → ④📴バナー＋鑑定が出れば合格。※Gmail等のアプリ内ブラウザはオフライン保存が効かないため、WebデモのオフラインテストはSafari直で行う。

## 9. メール配信システム（毎朝の手紙）

### 9.1 フロー
```
POST /api/subscribe（チャートを1回計算・保存。エンジン失敗なら503で誤保存しない）
 → 確認メール（double opt-in。確認まで1通も送らない）
 → GET /confirm → active
 → 毎時cron: node src/send-morning.js
     対象 = active かつ「本人の現地時刻 == send_hour（既定5）」 ← §4-地雷1
     保存済みチャート×今日 → 手紙合成 → 送信
     last_sent_on で同一現地日に冪等
 → GET/POST /unsubscribe（1クリック解除）
```
**決定事項**: 全世界・現地あさ5時統一。アカウントはメール＋パスワード。

### 9.2 API一覧
| Route | 説明 |
|---|---|
| `POST /api/subscribe` | `{email, consent:true, birthDate, birthTime?, sex?, lon?, off?, dst?, place?, nickname?, gender?, role?, countryOfOrigin?, timezone(IANA), sendHour?}` |
| `GET /confirm?t=` | opt-in確定 → 翌朝から配信 |
| `GET/POST /unsubscribe?t=` | 解除（List-Unsubscribe-Post one-click対応） |
| `GET /data?t=` / `POST /data/forget` | 任意プロフィールの本人確認/削除（CPRA）。誕生情報は残し配信継続 |
| `POST /internal/send-due` | cron用（要 X-Cron-Secret） |
| `GET /health` | 死活監視 |

### 9.3 DBスキーマ（SQLite・subscriber 1テーブル）
主要カラム: `email/email_verified`・`status(pending|active|unsubscribed|bounced)`・`plan`・`timezone/send_hour(既定5)`・`birth/chart(登録時1回計算のキャッシュ)`・`confirm_token/unsubscribe_token`・`last_sent_on(冪等キー)`・`consent_at/ip/ref(同意ログ)`・`attributes_forgotten_at`。
DBファイルは**必ず永続ボリューム**。数十万人まで実用、以降は `db.js` 差し替えで Postgres 化。

### 9.4 配信スケジューラ（send.js）
- cron は**毎時0分に1本**: `0 * * * * cd /path/to/clarity/server && node src/send-morning.js >> send.log 2>&1`（または Cloud Scheduler → `POST /internal/send-due`）
- 通常実行: active全員を走査し**本人の現地時刻==send_hour**の人だけに送る（§4-地雷1のルール厳守）
- `--hour 5`: 時計無視で send_hour=5 全員へ（テスト/バックフィル）。last_sent_on が二重送信を防ぐ
- 並列度 `SEND_CONCURRENCY`（既定20）。バウンス（Postmark ErrorCode 406）→ status='bounced' で以後送らない

### 9.5 手紙の生成
- テンプレ2種: `LETTER_TEMPLATE=briefing`（既定）/`classic`。内容はすべてエンジンの当日計算から（7段階ランク・理由・流年流月の一文・行動提案・ラッキーカラー・導線・SNSシェア・法定フッター）。
- **AI仕上げ（任意）**: `LETTER_AI=1`＋`GEMINI_API_KEY` の両方が揃った時のみ。事実の言い換えのみで発明しない。障害時は自動でテンプレ文へフォールバック（配信は止まらない）。

### 9.6 法令対応（実装済み）
CAN-SPAM: 全通に解除リンク＋`List-Unsubscribe(-Post)`・実在住所（`ORG_ADDRESS`は**番地まで必須**）・誠実な件名。double opt-in。同意ログ保存。CPRA導線（/data, /data/forget）。

### 9.7 プロバイダとDNS
Postmark（broadcastストリーム）。開発は `MAIL_PROVIDER=console`。DNS: DKIM＋Return-Path CNAME＋**DMARC必須**（`_dmarc TXT "v=DMARC1; p=none; rua=mailto:…"` → 様子見後 quarantine へ）。送信は `letter.numinous.app` 等のサブドメイン推奨。

## 11. サーバーデプロイ手順

最短は **GCE VM（推奨）**。SQLite・Chromium・cron が素直に載る。

1. Node 18+ ホストに **clarity/ ごと**配置（server は `../` のエンジンJSを相対参照——**フォルダ構造を崩さない**）
2. `cd server && npm install && npx playwright install chromium`
3. `cp .env.example .env` → §9.8 を埋める
4. `npm run verify:engine` → 全PASS
5. `npm run smoke` → 合格
6. `npm start` を常駐化（systemd等）
7. 毎時cron（§9.4）
8. DNS（DKIM/Return-Path/DMARC）
9. `app.html` の `LETTERS.BASE` と `BACKEND` を設定して資産再ビルド

Docker: 同梱 `server/Dockerfile`（Playwright公式イメージ）。Cloud Run の場合のみ DB を Cloud SQL 化（ディスク揮発のため）・メモリ1GB以上・cron は Cloud Scheduler。
