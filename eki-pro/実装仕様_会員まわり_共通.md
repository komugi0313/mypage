## 3. サーバーAPI仕様（16本 ＋ 決済結果の受け口）

- すべて **HTTPS／`POST`／`Content-Type: application/json`**（`gemini` だけ Google の generateContent 形式をそのまま通す）。
- **API_BASE**：フロントはパス `'/.netlify/functions'` を使う（名前は名残で、Netlify である必要はない）。`/.netlify/functions/<名前>` を各関数へリライトするか、下の定数を実URLに書きかえる（§9）。別オリジンにするなら CORS を許可する。
- **認証はトークン方式（必須）**：`auth-login` 成功時にサーバーがトークン（長期・失効可能）を発行して返す。フロントは**パスワードを端末に保存しない**（旧版の `member_pw`・`member_remember` は起動時に削除）。以後、マイページ・顧客カルテ・`gemini` は `Authorization: Bearer <member_token>`、`auth-check`・`auth-logout` は body の `token` で本人確認する。
- **商品の見分け**：フロントはすべての呼び出しにヘッダ `X-Product`（`pro`／`beginner`／`eki`）を付ける（§11-1）。あわせて呼び出し元のオリジン（`72k.ai`／`www.suimei.jp`／`ekipro.jp`）と、お申し込み番号の頭文字（`P-`／`B-`／`E-`）でも照合できる。**契約は「メール × 商品」ごと**に持ち、**トークンは発行したサイトの商品でだけ有効**にする（PRO のトークンで EKI を開けないように）。
- **body の `email` を信用しない**：`mypage-*`・契約系の API は、body の `email` ではなく**トークンの本人**のデータだけを扱う。

### 3-1. 認証・会員（8本）
呼び出し元：`auth.html`（ログイン・パスワード設定・設定メール・アドレスを忘れた/間違えた・アドレス変更の確定）、アプリ本体（`app-pro.html` 等。ログイン・確認・ログアウト）、マイページ（ログアウト）、料金ページの完了画面（アドレス直し）。
**会員は「テレコムクレジットの決済結果の通知」でサーバーが作る**（§4）。画面からの「新規登録」は無い（`auth.html?view=register` は料金ページ〈EKI は `register.html`〉へ転送）。

| API | body | 成功 | 失敗 | 役割 |
|---|---|---|---|---|
| `auth-login` | `{ email, password }` | `{ ok:true, status, email, token, periodEnd, usage }`（`usage` は §3-3） | HTTP 401（違う）／429・403（失敗が続いて一時的に止めたとき。画面は「しばらくログインできません」と案内） | ログイン。フロントは `member_email`・`member_token`・`member_status`・`member_period_end`・`member_checked_at` を保存（「ログインしたままにする」を外すと `member_token` だけ sessionStorage、`member_checked_at` は保存しない） |
| `auth-check` | `{ token }` | `{ ok:true, status, periodEnd, usage }`（`usage` は §3-3） | HTTP 401（無効・ログアウト済み） | アプリ起動時のログイン確認。401 ならログイン状態を消してログイン画面へ |
| `auth-logout` | `{ token }` | `{ ok:true }` | ― | トークンを失効。フロントは結果を待たない |
| `auth-setpw` | `{ token, password }` | `{ ok:true, email }` | HTTP 400／401／404／410（期限切れ・使用済み・見つからない。画面は「送り直し」へ） | 設定メールのリンク（`auth.html?view=setpw&token=…`）でパスワードを決める。初回と再設定で共通。パスワードは8文字以上（画面で確認済み）。トークンは短命・ワンタイム |
| `auth-reset` | `{ email }` | `{ ok:true }` | ― | 設定メールの送信。**登録の有無にかかわらず同じ応答** |
| `auth-email-hint` | `{ orderId }` | `{ ok:true, hint }`（例 `ta***@ex***.com`） | **HTTP 400 または 404**（body `{ ok:false }`） | メールアドレスを忘れた：お申し込み番号から登録アドレスの一部を返す。回数制限必須 |
| `auth-fix-email` | `{ orderId, email }` | `{ ok:true }` | **HTTP 400 または 404**（body `{ ok:false }`） | 申込時の打ち間違いをお客様が自分で直し、設定メールを送り直す。**パスワード未設定の会員に限る**・回数制限必須 |
| `email-change-confirm` | `{ token }` | `{ ok:true, email }` | HTTP 400 等＋`{ ok:false }` | マイページで申請したアドレス変更の確定（`auth.html?view=email&token=…`）。短命・ワンタイム |

- **ご契約状況の取得に失敗したら 2xx 以外で返す**：マイページは、2xx 以外や決まった `status` 以外の返事を「取得できなかった」として扱い、解約・カード変更を押せないようにする（2026-10-14 修正。以前は「ご契約がありません」と誤って出ていた）。
- **失敗は HTTP ステータスで返す**：料金ページの完了画面（`auth-fix-email`）は**HTTP ステータスだけ**で成否を判断する。HTTP 200 で `{ok:false}` を返すと「送り直しました」と表示されてしまう。

**`status`（契約ステータス）**

| status | 意味 | アプリ |
|---|---|---|
| `active` | ご利用中（課金中） | 開く |
| `trialing` | 無料お試し中 | 開く |
| `canceling` | 解約手続き済み（期間の最終日まで利用可・以後の請求なし） | 開く（`periodEnd` まで） |
| `canceled` | 解約済み | `periodEnd` の最終日までは開く。過ぎたら開かない |
| `past_due` | お支払いが確認できない（課金失敗） | 開かない（マイページでカード変更へ） |
| `unpaid` | 未払い | 開かない |
| `none` | 契約なし | 開かない |

- **`periodEnd` は必ず `YYYY-MM-DD`（日本時間の日付）**。フロントは整形せずに判定と表示に使う（マイページでは「2026-10-17まで」と表示）。
- 期間が満了した解約済みの会員は、`auth-check` で **401 ではなく `{ ok:true, status:'canceled', periodEnd }`** を返すと、画面が「ご利用期間が終了しました（解約済み）／お申し込みページへ」と案内できる（401 だとただのログイン画面になる）。
- 表示名：マイページの `STATUS_JA` は7種すべて対応。アプリ・`auth.html` の `statusJa()` は `canceling` 以外の6種（`canceling` はアプリが開くので表示されない）。
- 通信：アプリの会員ゲートは8秒で打ち切る（電波の弱い会場で止まらないように）。`auth.html`・マイページは打ち切りなし。

### 3-2. 顧客カルテ同期（2本・PRO とビギナーのみ）
呼び出し元：`app-pro.html`（ビギナーは生成された `app-beginner.html`）だけ。マイページ画面からは呼ばない。易 EKI Pro は使わない（顧客名簿は端末内のみ。規約にも「当社のサーバーには保存しません」と記載）。ログイン中（`member_email` あり）のときだけ同期し、未ログイン・サーバー未接続のときは端末内だけで動く。

| API | body | 成功 | 役割 |
|---|---|---|---|
| `mypage-get` | `{ email }`＋`Authorization: Bearer` | `{ data: <ドキュメント> }` | トークン本人のデータを返す |
| `mypage-put` | `{ email, data: <ドキュメント> }`＋`Authorization: Bearer` | `{ data: <保存後のドキュメント> }` | 保存（サーバー側でも統合。下記）。1会員あたり数MBを想定 |

**ドキュメント形式（`data`）** — フロントの `mpSanitize`（`app-pro.html` 7332〜7353行）が受け付ける形。決まった形以外の値は捨てられる：
```json
{ "schema": 1, "updatedAt": 0,
  "clients": [ {
    "id": "英数字と _- の1〜64字",
    "name": "お名前（〜100字）", "kana": "ふりがな（〜100字）",
    "date": "YYYY-MM-DD（必須。無い・形が違う人は端末側で捨てる）", "time": "HH:MM", "notime": false,
    "sex": "female | male", "pref": "出生地の経度（数字の文字列）", "corr": "full | longitude | none", "zishi": "today | next",
    "memo": "鑑定メモ（〜20000字）",
    "next": "次回お伝えすること（〜4000字・PROの「前回のふり返り」で使う）",
    "tags": ["〜40字 × 30個まで"],
    "readings": [ { "id": "…", "kind": "英数〜32字", "title": "〜200字", "text": "〜200000字", "ts": 0 } ],
    "ts": 1727600000000, "deleted": false
  } ] }
```
- 削除した人は `{ id, deleted:true, ts }` だけが残る（名前・メモ・鑑定は空になる）。**サーバーはこの形をそのまま保存して返す**。
- **統合の規則（フロントの `mpMerge` と同じにする）**：両方の `clients[]` を `id` ごとに比べ、`ts`（更新時刻）が新しい方を採用。同じ `ts` なら後から渡した側（フロントではサーバーの応答）を採用。`deleted:true` は消えた印として残す（複数端末でも消えたまま）。`updatedAt` は両者の大きい方（フロントは更新しない）。
- **`mypage-put` の返事で端末のカルテを丸ごと置きかえず、統合する**（フロント実装済み）。サーバー側も、受け取ったデータで既存データを消さないよう統合する。
- 端末の保存キー：ログイン中は `bazi_mypage_v2@<メールアドレス>`（会員ごと）、未ログインのときは `bazi_mypage_v2`（ログインしたときに会員のキーへ引き継ぐ）。`bazi_clients_v1` は旧形式（初回の移行用）。
- **解約後のデータ**：規約 第12条・プライバシーポリシー 7 で「サーバーの顧客カルテは解約から1年間保管し、その間に再契約して同じメールでログインすれば引き継がれる」と約束している。再契約後の `mypage-get` は同じメールのデータを返す。1年を過ぎたら削除。
- **ロック中の書き出し**：解約後・期限切れでアプリがロックされていても、ロック画面の `#mg-export` から**その端末でログインしていた会員の分（と未ログイン時の分）だけ**を JSON で書き出せる（共用の端末でも、ほかの会員のカルテは書き出さない。2026-10-13 修正）。認証ゲートを作り直すときも消さない。
- ログアウト時、アプリは顧客カルテをサーバーに保存できたことを確かめてから端末から消す（保存できないときは端末に残し、その旨を表示）。

- EKI：`app/index.html`（鑑定・深掘り相談・鑑定書）。

いずれも URL は定数ではなく `'/.netlify/functions/gemini'` と直接書いてある（`app-pro.html` 6452行・`meishi-sheet.html` 4234行・`app-beginner.html` 6471行・EKI `app/index.html` 2737行）。`netlify.toml` では `/api/gemini` も同じ関数の別名。

**APIキーは絶対にフロントに出さず、サーバーの環境変数で持つ。** 雛形 `functions/gemini.js`（3サイトとも同じ仕組み。EKI は全体の大きさの上限だけ5,800,000字）あり。

```json

  "system_instruction": { "parts": [ { "text": "…指示…" } ] },
  "contents": [ { "role": "user", "parts": [ { "text": "…相談内容と命式データ…" } ] } ],
  "generationConfig": { "maxOutputTokens": 1536, "thinkingConfig": { "thinkingBudget": 0 } }
```

- `maxOutputTokens`：PRO・ビギナーは **1536（冒頭の答え）／3072（くわしい読み解き・全文）**、鑑定書は **3200**。EKI は **4096**（`temperature: 0.8`）。`thinkingConfig` は、PRO・ビギナーのアプリでは flash 系のときだけ付く。EKI は常に `thinkingBudget:0`。鑑定書は付けない（雛形が flash 系では必ず0にする）。
- **ヘッダ**：
  - `Authorization: Bearer <member_token>`（会員確認。フロントが自動で付ける）
  - `x-pk-deep: 1` … 深め（DEEP）の鑑定（自動鑑定・鑑定書など）。サーバーは `GEMINI_MODEL_DEEP` を使う

  - `x-eki-kind: sho` … 易の鑑定書の作成。**回数に数えない**

- **相談で送る文章は、質問に関係する分だけ（2026-10-16）**：相談（`doConsult`）では、命式データ全文（約2万字）ではなく、`consultChartText(c, topics)` で質問のテーマ（`consultTopics`：恋愛・仕事・お金・健康・移動・人生・人間関係・自分）に合う項目と、時期の判断に要る項目（四柱・五行と身旺身弱・喜神忌神・大運／年運／月運／日運・今後5年・30年の流れ〈節木運〉・人生の時間軸・各時期に巡る星の意味・合冲・会局・空亡期・天戦地冲 など）だけを送る。**時期の材料はどのテーマでも必ず送る**（恋愛・結婚・人間関係は日運・月運・年運・大運・30年の流れで答えが変わるため。発注者指示 2026-10-16）。聞かれていないテーマ（恋愛の相談でのお金など）は送らない・書かせない。指示（`CONSULT_SYSTEM`）も、関係しないテーマ別の段落（お金・健康・心・恋愛の繊細なテーマ）を外す（`consultSystemSlim`）。相談1件で送る量は約6.2万字→約4.2〜5.3万字。自動の詳細鑑定・鑑定書は全文のまま。`app-pro.html` の `PK_SLIM_PROMPT=false` で元の全文に戻せる。**本番前に `tools/live_ai_test` で、文章の質が落ちていないか（根拠の星・時期が出ているか）を確かめる**。

## 4. 決済（テレコムクレジット）とお申し込みの流れ

> 3商品とも**同じ流れ・同じAPI**。料金は **月額 9,800円（税込）のみ**（`PLAN.month`）。

### 4-1. 流れ（お客様の画面）
1. **申込画面**（PRO `pricing-pro.html`／ビギナー `pricing.html`／EKI は `register.html` でお名前・任意のプロフィールを入れたあと `upgrade.html`）：メールアドレスを**2回入力**（不一致はエラー）＋規約・特商法・プライバシー・自動更新への同意 → **最終確認画面**（特商法：メール・プラン・料金・無料期間の終了日・初回課金日・更新日・解約期限・回数上限・解約と返金を表示）。
2. 「この内容で申し込む（決済ページへ）」→ フロントが**お申し込み番号**を作り（`P-YYYYMMDD-XXXXX-XXXXX`。ビギナー `B-`、EKI `E-`。英大文字と数字で I・O・0・1 は使わない。日付は端末の日付）、`TELECOM_PAYMENT_URL` に**お申し込み番号とメールアドレス**を付けてテレコムクレジットの決済ページへ移動（パラメータ名は `TELECOM_PARAM`。**接続仕様書の名前に合わせて書きかえる**）。`TELECOM_PAYMENT_URL` が空の間は「準備中」と表示して進まない。
3. お客様が決済ページでカードを登録（無料期間付きの継続課金）。
4. **テレコムクレジット → サーバーへ決済結果の通知**（サーバー間）。サーバーは通知を仕様どおり検証し、お申し込み番号・メールで**会員を作成（`status=trialing`）**、「ログイン用パスワードの設定」メール（`auth.html?view=setpw&token=…`）を送る。同じ通知が何度来ても1件だけ作る（お申し込み番号で重複を防ぐ）。
5. 決済ページの**戻り先**：PRO `pricing-pro.html`／ビギナー `pricing.html`／EKI `upgrade.html` の `?result=ok`（完了：送り先メール・お申し込み番号・届かないときの案内。番号とメールはこの端末の `pending_order` から表示）／`?result=ng`（中断・失敗。`?result=back` も同じ表示）。**戻り先URLの表示だけで会員を作らない**（URLは誰でも打てる）。
6. メールのリンクでパスワードを決める → ログイン → アプリ。
7. 無料期間は**お申し込み日を1日目とする7日間**。**8日目に初回 9,800円** → `active`。以後その日が毎月の更新日（**その日がない月は月末日**）。次回の請求を止める期限は**更新日の前日23:59（日本時間）**。課金失敗 → `past_due`（アプリは開かず、マイページでカード変更へ誘導）。
8. **無料期間の終わりのお知らせはしない**（発注者決定 2026-10-13。終了前のお知らせメールなし）。代わりに、**何日まで無料で、何日から自動で月額9,800円になるか**を、確認画面・完了画面（`?result=ok`。`pending_order` の日時から日本時間で計算）・マイページ・特商法に日付で明記し、「終了前のお知らせメールはお送りしません」とも書いている。**パスワード設定メールにも、無料期間の最終日と初回課金日を日付で書く**。あわせて**お申し込み番号も書く**（別のブラウザで決済した等で完了画面に番号が出ないことがあり、「メールアドレスを忘れた・間違えた」に必要なため）。

- **モデルの注意（2026-10-16 確認）**：Google は 2026-09-18 から、2.5系（`gemini-2.5-flash` など）を「最近使っていた利用者だけ」に限っている（終了の発表はないが、**新しく作るプロジェクトでは使えないことがある**）。新しいプロジェクトには `gemini-3.5-flash-lite`（料金は 2.5 Flash と同じ 入力$0.30／出力$2.50 per 1M・第三者の価格表による）または `gemini-3.8-flash`（入力$0.75／出力$3.75、2027-01-01 から2倍の予定・同）が案内されている。本番の API キーで 2.5 が使えなければ `GEMINI_MODEL`・`GEMINI_MODEL_DEEP` を `gemini-3.5-flash-lite` にする。雛形は名前に `gemini-3` を含むとき `thinkingBudget:0` を外して出力の上限を広げるが、**3系は考える分（thinking）も出力として課金される**ので、3系の思考を最小にする設定（`thinkingConfig` の `thinkingLevel` 等）を公式の資料で確認して入れ、原価ログ（`[pro-cost]`・`x-pk-tok`）で相談1件あたりの費用を測り直すこと（回数の上限は1件 約4.5円で計算している）。

- **雛形は Netlify Functions 用の書き方**（`exports.handler`、`event.httpMethod/headers/body` を受けて `{statusCode,headers,body}` を返す。数えるのは `@netlify/blobs`）。他の基盤で動かすときは作り直す。
- 雛形が返すエラー：401 `LOGIN`、403 `MEMBER`／`ORIGIN`、405（POST以外）、413 `TOO_LONG`（`role:'user'` の付いた最後の入力が40,000字超、または全体が900,000字超。EKI は `role` を送らないので全体の上限5,800,000字だけが効く）、429 `BUSY`、451 `REGION`、500 `NO_KEY`、502 `UPSTREAM`、503 `SETUP`／`MEMBER_CHECK`。
- 雛形のやり直し：通常（DEEP でない）呼び出しが Google から 429 のときは0.9秒後に1回だけ再試行。DEEP が失敗したら、`GEMINI_MODEL_DEEP` と `GEMINI_MODEL` が違うときだけ通常モデルで1回やり直す（既定は同じなのでやり直さない）。

## 7. セキュリティ必須事項

1. **`GEMINI_API_KEY` はサーバーのみ**。本番でテスト用キー欄を削除（§2 #4）。
2. 全通信 HTTPS。パスワードはハッシュ保存（bcrypt／argon2 等）。
3. トークン認証：`auth-login` で発行したトークンを `auth-check`・`mypage-*`・契約系・`gemini` で検証。ログアウト・パスワード変更で失効。
4. `auth-*` は回数制限・総当たり対策。設定メール・変更メールのリンクは短命・ワンタイム。
5. 決済結果の通知はテレコムクレジットの仕様どおり検証してから反映。戻り先URL（`?result=ok`）では会員を作らない。
6. 契約・マイページ系の API は、body のメールではなくトークンの本人だけを扱う。

## 11. 共通基盤（今後のすべての商品・Web とアプリの両方を、同じ基盤につなぐ）

> **発注者の方針（2026-10-14）**：今後、toC（一般の方向け）・toB（占い師・事業者向け）の商品を**たくさんリリースする**。**商品にかかわらず、必ず同じ基盤につなぐ**。Web 版のほかに**アプリ版（iOS・Android）**も出す。決済は Web ではテレコムクレジット。
> この3サイト（PRO・ビギナー・易 EKI Pro）は、その基盤につなぐ最初の3商品として作ってください。**4つ目以降の商品を、基盤の作り直しなしで足せる**ことが要件です。

### 11-1. 商品の見分け方（フロント実装済み）
- フロントは、サーバーAPI（パスが `/.netlify/functions/…` または `/api/…`）を呼ぶとき、**必ずヘッダ `X-Product: <商品ID>`** を付ける（2026-10-14 実装）。今の商品IDは `pro`／`beginner`／`eki`。
  - 仕組み：各ページの `<head>` 先頭の `<script id="pk-product">`（`tools/add_product_tag.py` が埋め込む）が、`fetch` に自動でヘッダを足す。アプリ版のように**絶対URLで別ホストのAPIを呼んでも付く**。Google への直接の呼び出し等には付けない。
  - 鑑定書（`meishi-sheet.html`。3か所でバイト同一のため埋め込まない）は、同じサイトのアプリが書いた `localStorage['pk_product']` を読んで付ける。
- 基盤は `X-Product` を**目印**として使い、**本人確認と商品の確定はトークン**で行う：トークンの商品と `X-Product` が違えば 403。`X-Product` が無い呼び出し（更新前の端末に残った古い画面など）は、Origin・トークン・お申し込み番号の頭文字で判定する。
- お申し込み番号の頭文字は商品ごとに重ならないようにする（1〜4文字の英大文字。今は `P`／`B`／`E`。画面の番号チェックは1〜4文字に対応済み）。
- 別ホストのAPIを呼ぶ構成（アプリ版・API専用ドメイン）では、CORS で `Content-Type`・`Authorization`・`X-Product`・`x-pk-deep`・`x-pk-part`・`x-pk-device`・`x-eki-kind` を許可する。

### 11-2. 商品マスタ（基盤に持つ。新しい商品は1行足すだけで動くように）
| 項目 | 例（PRO） |
|---|---|
| 商品ID（`X-Product`） | `pro` |
| 表示名・種別 | 四柱推命 自動鑑定 PRO・**toB**（toC／toB） |
| Web のオリジン | `https://72k.ai`（複数可） |
| アプリのID | iOS バンドルID・Android パッケージ名（アプリ版を出すとき） |
| お申し込み番号の頭文字 | `P` |
| 料金・無料日数 | 月額 9,800円（税込）・7日 |
| 回数上限 | ご契約の1か月で700回・1日の上限なし・無料期間中は1日3回（EKI は 1か月1,400回・1分15回、無料期間中1日3回） |
| 回数に数えない目印 | `x-pk-part: detail`（EKI は `x-eki-kind: detail`／`sho`） |
| テレコムクレジット | 決済ページURL・店舗の識別子・パラメータ名・結果通知の検証方法 |
| メール | 差出人の表示名・各メールの文面（商品名・ログインURL・マイページURL） |
| 文章生成 | 使うモデル・原価の上限 |
| 規約の版 | 同意した規約・特商法の版（いつ、どの版に同意したか） |

- API・決済結果の受け口・メール送信・定期処理・回数上限は、**商品マスタを見て動く1つの仕組み**にする（商品ごとにサーバーをコピーしない）。
- 契約・トークン・回数・顧客カルテ・無料体験の記録（`trial-check`）は、すべて**商品ごと**に持つ。

### 11-3. アカウント：商品ごとに別のログイン（発注者決定 2026-10-14）
- **商品ごとに、別々のアカウント・ログインにする**（共通IDにはしない）。商品ごとにターゲットも中身も違う、別の商品のため。
- 同じメールアドレスの人が複数の商品を契約しても、**パスワード・ログイン・マイページ・パスワード設定メール・回数・顧客データは商品ごとに別**。ある商品でパスワードを変えても、ほかの商品には影響しない。
- 今の画面・規約・プライバシーポリシーはこの形のままでよい（手直し不要）。
- 基盤は1つ（同じサーバー・同じ仕組み）で、アカウントの表は「メール × 商品」を1件として持つ。トークンは発行した商品でだけ有効（§11-1）。

### 11-4. 決済
- **Web**：テレコムクレジット。結果通知の受け口は全商品で1つ（お申し込み番号の頭文字と商品マスタで商品を決める）。
- **アプリ版**：アプリの中でデジタルの機能を販売する場合、Apple・Google は原則ストア内課金を求める。契約に「どこで支払ったか（`telecom`／`apple`／`google`）」を持ち、`status` は共通にする。Web で契約した人がアプリでログインして使えるか、アプリ内に Web の申込画面へのリンクを置けるかは、ストアの規約に従って確認する（料金・手数料が変わる可能性があるので、方式は発注者と決める）。
- **toB の商品**：適格請求書（インボイス）・領収書の発行、法人名の入力、請求書払いの要否を商品ごとに決められるようにしておく。
- **toC の商品**：特商法の最終確認画面（今の申込画面と同じ作り）、未成年の扱い（規約）、解約のしやすさを、今の3商品と同じ水準で。

### 11-5. アプリ版にするときの注意（今の画面をアプリに包む場合）
- API は絶対URL（例 `https://api.72k.ai/…`）にする（各ページの API の定数。§9）。アプリの中は `localhost` 等のため相対パスの `/.netlify/functions` は届かない。
- **本番ドメインの安全装置（§2）がアプリの中では効かない**ので、`PREVIEW_MODE=false`・`STUB=false` を必ず書きかえる（書き忘れると誰でも全機能が使える）。
- 送信元は iOS `capacitor://localhost`、Android `https://localhost` になる。`ALLOWED_ORIGINS` に足すか、アプリ用の確認方法にする。
- テレコムクレジットの申込画面は、アプリの審査方針に合わせて出し分ける（11-4）。
- 端末内のデータ（顧客カルテ・名簿）はアプリを消すと消えるので、書き出し（バックアップ）の案内は残す。
- リポジトリ直下の `app/` に Capacitor の土台あり（§8）。

### 11-6. 新しい商品を足すときの手順（フロント側）
1. フォルダを用意する（既存の商品をもとに作る）。
2. `tools/add_product_tag.py` の `PRODUCTS` に「フォルダ: 商品ID」を1行足す。
3. 申込画面の `ORDER_PREFIX`（重ならない頭文字）・`TELECOM_PAYMENT_URL`・`TELECOM_PARAM`。
4. 各ファイルの本番ドメインの判定式 `/(^|\.)(72k\.ai|suimei\.jp|ekipro\.jp)$/` に新しいドメインを足す。
5. 規約・特商法・プライバシーポリシー（商品名・販売URL・料金・回数上限）。
6. `python3 tools/add_contrast_guard.py` → 生成スクリプト → `python3 tools/add_product_tag.py` → `sw.js` の `CACHE` を上げる。
7. 基盤の商品マスタに1行足す（11-2）。
